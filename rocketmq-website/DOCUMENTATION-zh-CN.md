# 编写 RocketMQ-Rust 文档

[English](DOCUMENTATION.md) · [网站开发](README-zh_cn.md)

面向需要搭建系统、使用 API、解释故障或理解设计取舍的读者写作。先说明结果和适用条件，让读者知道下一步做什么，不必从多份 crate README 中重新拼接操作步骤。

## 选择页面类型

| 类型 | 读者的问题 | 内容 |
| --- | --- | --- |
| 教程 | 怎样获得第一个可工作的结果？ | 目标、前提、完整步骤、预期现象、失败处理、关闭、下一步 |
| 操作指南 | 怎样完成这项操作？ | 场景、适用拓扑、权限、受影响资源、过程、观察、恢复 |
| 技术设计 | 系统为什么这样工作？ | 问题、边界、所有权、数据流、不变量、异常行为、取舍、实现来源 |
| 参考手册 | 这个选项或接口是什么意思？ | 精确名称、类型、默认、单位、条件、约束、示例、兼容性 |

教程聚焦一条完整路径，其他选择放进对照表或独立操作指南。架构文档通过职责和状态变化解释设计，单纯罗列源文件无法说明设计理由。

## 同时编写英文与中文

英文原文与简体中文文档使用对应路径：

```text
docs/architecture/runtime.md
i18n/zh-CN/docusaurus-plugin-content-docs/current/architecture/runtime.md
```

新页面默认由内容根目录下的路径形成文档 ID。编辑已有页面前先查看 front matter，保留显式 `id`、`slug` 和原有 URL。中文需要完整覆盖前提、限制、恢复、图注和替代文本；中文摘要或英文回退不算完整译文。

两种语言使用相同的 API 名、配置键、命令选项、数值和示例逻辑。Broker、NameServer、Controller、Proxy、Topic、Consumer Group、CommitLog、ConsumeQueue 等标识保持原文，首次出现时解释不熟悉的术语。

使用站点支持的常规 front matter：

```yaml
---
title: 运行时架构
sidebar_label: 运行时
description: 任务所有权、资源预算、取消与关闭。
---
```

英文页面提供对应显示字段。不要在 `docs/` 下再建一套语言目录，也无需引入元数据登记系统。

## 明确技术结论的范围

使用所描述版本的实现、配置加载器、manifest、相关示例和公开契约。模块 README 用于定位；涉及默认值、feature、协议注册或构造方式时，继续查看实际入口。

分别回答以下问题：

- **已经实现：** 是否存在具体实现？
- **已经启用：** 哪些编译 feature、运行配置和适配器使其生效？
- **实际观察：** 哪个场景真正编译、运行或演练过？
- **已经发布：** 已发布版本是否包含所描述的发行物？

导出的 API 不等于所有运行路径都已接线，工作流文件存在不等于场景已经运行，Cargo 包版本也不等于发行公告。准确说明尚未确定的条件，继续完成已有事实支持的内容。

当前网站将开发中文档标为 **1.0.0 开发版**。根源码选择 Rust 1.95.0，包版本为 1.0.0；这些值描述源码树，不承诺 1.0.0 二进制或 crate 已经发布。特定发行版的说明链接到对应 release，不把旧 crate 依赖和当前源码示例混在一起。

## 让命令具有完整上下文

每组命令先说明工作目录、操作系统或 shell、配置输入，以及需要提前运行的服务。完整示例包含初始化和关闭，不能只保留中间的发送或接收调用。

根 Cargo workspace 不包含所有产品。`rocketmq-example`、部分 Dashboard 工程和 AI 工程具有独立 manifest 或 workspace，使用各自命令和本地指南。根构建成功不能证明这些独立工程已经构建。

每个操作步骤分别说明：

1. 命令读取或修改什么。
2. 读者应该观察到什么输出或状态。
3. 观察缺失或异常意味着什么。
4. 怎样停止或恢复，并保留无关数据。

使用占位凭据，在适用位置解释本地开发例外。代码节选和伪代码明确标注。命令如果只与源码核对、尚未运行，应如实说明，不编造输出或生产恢复保证。

## 在正确的边界解释可靠性

区分接纳、本地持久性、副本确认、派生索引可见性、消费和业务处理。超时可能意味着结果未知，不一定表示没有写入。避免无条件的“不丢消息”“恰好一次”或吞吐承诺。

性能数字需要负载、环境、配置和测量上下文。恢复流程需要备份边界、前提和已知限制。缺少这些信息时，解释设计或过程，不附加缺乏依据的数字。

配置参考需要从解析器或 Serde 实现核对外部名称和默认值。Rust 字段名可能不同于配置键，字段存在也不意味着支持热更新。

## 使用便于维护的图示

拓扑、所有权、时序、状态和信任边界优先使用 Mermaid 或可编辑矢量图。网站已启用 Mermaid。进程边界与 crate 依赖分开标注，解释箭头含义，并在图后提供简短文字说明。

图内标签、图注和替代文本分别提供英文与中文；API 等标识保持不变。无文字图像可共享一个文件，需要不同语言的矢量图可以使用 `.en.svg` 和 `.zh-CN.svg`。

图片放在 `static/img/docs/<topic>/`，沿用网站静态资源引用方式。查看深浅色主题和窄屏下的可读性，不能只靠颜色区分角色或状态。

图片模型可以生成概念插图或无文字背景。作者应按文章核对关系，必要时标明概念示意。生成图不能冒充真实产品截图、基准测试或精确协议图。

## 内容扩展时保留导航

将已经写成的文档 ID 加入 `sidebars.ts`，在 `i18n/zh-CN/` 翻译分类和导航。当前 sidebar 是手写列表，`_category_.json` 不能替代其中的显式页面项。

尽量在原 URL 重写现有内容。合并页面时保留有用的简短介绍和目标链接；静态 GitHub Pages 不会自动提供服务端 HTTP 301。

观测配置与监控操作流程分开维护。新的任务指南完成后，再整合重复 FAQ 和性能建议。保留作者/社区入口，将发布信息引向配置中的 `releases` 栏目。

## 直接校对变更

通读两种语言，打开受影响链接，查看代码块和图示。实际修改网站正文、路由或配置时，从本目录运行既有构建：

```bash
npm run build
```

使用 `npm run start` 或 `npm run start:zh` 预览对应语言。复用已有依赖，缺少依赖或 lockfile 变化时再运行 `npm ci`。不要提交 `.docusaurus/`、`build/` 或 `node_modules/`。

文档编写不需要文件指纹、哈希、固定提交、评分、阶段审批或新的 CI 门禁。简短记录实际完成的检查和未运行的环境；无关历史失败不要求先修复整个仓库才能完成文章。

产品认证、授权与审计影响用户操作时，仍需在技术文档中说明。简化写作过程不会改变这些运行要求。
