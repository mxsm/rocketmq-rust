# Instance ownership and module responsibilities

This record tracks W12, W13, W14, and W16 from the September 8 remediation plan.
W12, W13, W14, and W16 are implemented and locally verified. The
[activation and health contract](2026-09-08-activation-and-health.md) records
the initial policy and configuration semantics.

## Frozen filter registries

`FilterRegistryBuilder` validates required SQL92 support and rejects duplicate
bindings before consuming itself to produce an immutable registry. Broker bootstrap
accepts that registry explicitly. Client configuration checks and subscription
registration use the same manager and positive/negative compilation cache.

Cache keys include the registry identity, expression type, and expression text.
Compiled expressions retain the registry throughout evaluation and when consumer
filter data is cloned. Persisted consumer filter data keeps its existing fields;
the registry and compiler remain runtime-only objects.

The global `FilterFactory` retains its legacy registration semantics. Production
custom compilers must be supplied through `broker_bootstrap::Builder::with_filter_registry`
before startup. Changing compiler bindings requires a restart. The legacy SQL92
lookup now also offers a fallible entrypoint.

## Authentication providers and lifecycle

`ProviderBundle` binds user and ACL data ports, separate lifecycle controls, and an
optional ACL snapshot import capability. `SubjectKey` provides an owned identity at
the dynamic boundary. Boxed, Send futures keep the data ports object-safe without
requiring a global lock around concurrent provider requests.

The runtime validates its built-in authentication/authorization provider selection
and required import capability before initializing a supplied candidate. It then
initializes controls, seeds users, imports ACL data, prepares services, and registers
the watcher. Failures reverse attempted controls, including partially initialized
controls, and retain the primary error and all provider cleanup errors.
`AuthStartupFailure` exposes the primary cause and an explicit cleanup retry when
rollback times out or fails. Neither dropping this error nor dropping a runtime is
an asynchronous shutdown operation.

Shutdown closes admission, stops the watcher, drains admitted work, flushes and
closes controls in reverse order, then stops owned metadata I/O and tasks. Every
step uses the same absolute deadline. Timeout or caller cancellation retains the
provider finalizer; subsequent calls resume it. Successfully completed controls
are not finalized twice. Runtime clones share the owner and shutdown result.

Broker Auth administration, runtime services, handlers, and registry-based managers
use guarded data handles. Proxy authentication and authorization admit their entire
entrypoint operation, including remote metadata synchronization and whitelist paths,
so shutdown cannot close providers while those operations are outstanding.

Factory calls supplied with a registry use its actual providers and instance-owned
strategy caches. Registry generation invalidates stateful decisions, and closed
admission is checked before returning a cached result. Factory calls without a
registry retain their explicit legacy cache behavior. Registry-based compatibility
managers borrow data handles; their shutdown releases those handles while the
runtime retains lifecycle responsibility. Provider replacement requires a restart.

Operational user lookup failures remain distinct from missing users and invalid
credentials. Public errors remain redacted while trusted diagnostics retain typed
causes. Auth metadata formats, subject keys, signing content, and protocol fields
are unchanged.

## Shared administration and narrower Store reads

Topic deletion now has one core request and outcome contract for CLI and TUI.
The use case validates both constructed and deserialized requests, normalizes
master targets, retains every Broker outcome, and removes NameServer routes only
after all Broker deletions succeed. The SDK adapter retains the existing
`ServiceAdminSession` lifecycle and error conversion. TUI deletion now supplies its
caller-owned `ClientRuntime`; its previous compatibility entrypoint could not start
a session. CLI completion uses the shared result projection, including both the
legacy permission code and its canonical equivalent. Existing service-module model
exports and serialized fields remain compatible.

Client metadata pagination lives in the private `admin/metadata.rs` module. Topic
and subscription-group reads share their transport outcome mapping, response
validation, page-size conversion, and operation timeout owner. Version changes
restart assembly within the original timeout. Request codes, Java header names,
pagination rules, and legacy responses without advertised totals are unchanged.

`BrokerReadStore` no longer exposes `Any`, Store configuration, a concrete
CommitLog, raw replication chunks, or administrative runtime maps. Administrative
consumers use `BrokerAdminStore`; replication consumers use
`BrokerReplicationStore`. These are source-level capability-bound changes, with
the backend implementation contract and persisted formats retained. Broker Lite
administration uses an owned queue-count result. Ordinary Lite reads, cold-data
checks, and scheduled delivery use typed Store operations. Schedule offset
correction uses the existing `find_consume_queue` port and reports failure when a
backend cannot provide the queue, removing its concrete downcast and panic.

## Validation

W16 adds an owned Proxy dependency monitor with configurable failure/recovery
hysteresis and freshness expiry. Local checks actual Broker startup and Store
writability. Cluster performs fresh routing and one read-only Broker metadata
request under a shared deadline. A separate lifecycle dependency gate preserves
maintenance and shutdown precedence. Startup finalization cancels and awaits the
monitor before the backend. Broker runtime configuration responses distinguish
applied values from persistence with additive extension fields.

  listener and injected-registry client validation regressions.
- Auth: 375 unit tests passed, including provider/cache isolation, initialization,
  seed/import/watcher failure rollback, cleanup error retention, initialization versus
  shutdown, in-flight drain, retained close futures, and metadata I/O shutdown ordering.
