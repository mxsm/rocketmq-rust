# Core deployment configuration and runtime validation

This phase updates the packaged `distribution/helm/rocketmq-rust-core` chart.
Its deployment contract is `files/deployment-policy.json` inside the chart;
the core packager, container guard, and tests share that declaration through
`distribution/core_helm_contract.py`.

## Runtime configuration

NameServer, Broker, and Controller use StatefulSets with retained PVCs. Helm
renders one complete TOML file per ordinal. The downward API supplies `POD_NAME`,
and Kubernetes expands it in the executable's `-c /etc/rocketmq/$(POD_NAME).toml`
argument. No shell is required. Proxy uses a fixed `service.toml` and a Deployment.

| Profile | Runtime behavior |
| --- | --- |
| `values-dev-single.yaml` | One NameServer and one asynchronous master; local development scope |
| `values-production-default-ha.yaml` | Two NameServers and one synchronous master/one slave, with two required in-sync replicas |
| `values-production-controller-ha.yaml` | Two NameServers, three Controller voters and three Broker replicas; Controller assigns roles, with at least two in-sync replicas |
| `values-production-proxy-tls.yaml` | Default HA topology plus two cluster-mode Proxies serving TLS on the configured gRPC port |

Broker identities and advertised addresses are unique per ordinal; each replica
group retains one broker name. Controller IDs start at one and use separate
advertised remoting and Raft DNS endpoints. New `raftPeerEndpoints` and
`controllerPeerEndpoints` preserve DNS names through serialization and transport
connection. Legacy IP-only `raftPeers` and `controllerPeers` retain their existing
types and behavior. Mixing the two membership representations is rejected.

Peer discovery uses headless Services with `publishNotReadyAddresses`. Separate
client Services expose the public listener. Advertised names are cluster-internal
DNS names. Production profiles require distinct hosts for replicas of each
service, with additional best-effort zone spread.

Readiness and liveness use `/readyz` and `/livez`; preStop calls `/drainz`. The
default process shutdown budget is 45 seconds and the Pod grace period is 60
seconds. Both preStop and the subsequent signal use the existing process shutdown
deadline. Resource requests/limits, PVC retention, storage class, listener ports,
Proxy control reserve, and replication minima are validated before deployment.

TLS and ACL material come from existing Secret references. Authentication is
disabled by default; `services.<service>.auth.enabled` projects both authentication
and authorization plus the ACL file path. Clients must supply credentials that
match the deployed ACL. Proxy TLS requires a binary built with `tls`; client
certificate modes additionally project the configured CA key. The chart never
generates credentials or certificates.

Configuration changes update a Pod-template checksum. StatefulSets use `OnDelete`
for controlled restarts; Proxy rolls with zero unavailable replicas. Controller
identity, membership, listener, and storage settings are restart-required in the
rendered configuration.

## Current validation results

Helm lint and template checks pass for all four profiles. Sixteen Python regressions
cover rendered configuration, identity, HA roles, resources, probes, PVC retention,
Secret projection, network selectors, invalid value combinations, packaging, and
the one-Pod rollout operator's refusal and replacement behavior.

The real Rust loaders accepted all 19 exported configurations: eight Broker,
three Controller, seven NameServer, and one Proxy. NameServer validation invokes
the binary's configuration merge path, including its transport overrides. Proxy
validation uses `--no-default-features --features cluster-mode,tls`.

Reproduce the configuration checks with Python 3.11+, PyYAML, and Helm:

```bash
python -m unittest scripts.tests.test_core_helm_rollout scripts.tests.test_core_helm_runtime scripts.tests.test_core_container_image_guard scripts.tests.test_package_core_helm
python scripts/core_helm_configs.py --output /tmp/core-helm-configs
export CORE_HELM_CONFIG_DIR=/tmp/core-helm-configs
cargo test -p rocketmq-broker -p rocketmq-controller --test core_helm_config -- --ignored
cargo test -p rocketmq-namesrv --bin rocketmq-namesrv-rust rendered_core_helm_configs_use_namesrv_loader -- --ignored
cargo test -p rocketmq-proxy --no-default-features --features cluster-mode,tls --test core_helm_config -- --ignored
```

The Controller rollout observation uses a bounded ReadIndex barrier followed by
fresh Raft acknowledgements and matched log positions. A three-node in-process
gRPC test confirms that an offline peer's old replication position cannot permit
restarting a second voter. Replacing the failed voter remains possible while the
other two voters form a quorum. The test drains and awaits its RPC task groups.

The observation is opt-in through `checkQuorumForNode` on metadata request 1005.
Ordinary Java metadata requests retain their existing headers and empty body;
focused request-processor tests verify that behavior and rejection of invalid
targets and single-voter rollout requests.

Apache RocketMQ 5.3.3's [Controller metadata handler](https://github.com/apache/rocketmq/blob/rocketmq-all-5.3.3/controller/src/main/java/org/apache/rocketmq/controller/processor/ControllerRequestProcessor.java)
does not inspect this extension. The rollout client rejects a missing or
unsupported observation body; an ordinary successful metadata response alone
cannot authorize a restart.

## Controlled Controller restart

`rocketmq-admin-cli getControllerMetaData --check-quorum-for-node <id> -a <leader>`
uses the existing authenticated Admin session and prints a versioned JSON result.
The response names the current voters and their actual Raft endpoints. Ordinary
metadata output is unchanged. The Protocol and Client tests reject malformed,
unsupported, denied, or insufficient observations; two CLI tests cover the
existing command and explicit nonzero target selection.

The packaged `files/rollout.py` reads the selected StatefulSet's rendered peers,
checks their identity against the fresh observation, and submits one Pod eviction
with a UID precondition. It requires the matching majority PDB and never bypasses
a refused eviction. Completion requires a new Ready, non-terminating Pod owned
by the same StatefulSet. See the chart [operator instructions](../../../distribution/helm/rocketmq-rust-core/README.md).

The latest three-voter regression passed in 6.10 seconds, including two rejected
checks after one voter stopped. That duration measures the bounded refusal paths
in this test; it is not failover RTO. The check reserves no future availability and
must be repeated before each restart. Kubernetes deployment, actual Pod eviction,
PVC recovery, and production reliability remain untested here.

An actual Java RocketMQ 5.5.0 Netty client also passed metadata and rollout
rejection checks in both JSON and ROCKETMQ binary encodings. The complete
[selected validation record](2026-09-08-validation.md) distinguishes those results
from deployment and performance scenarios that were not executed.
