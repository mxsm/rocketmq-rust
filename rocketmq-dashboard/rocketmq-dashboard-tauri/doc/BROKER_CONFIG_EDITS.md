# Broker configuration edits

The Cluster page lists Brokers in the selected cluster and shows Runtime or Configuration details for the selected identity. Filtering does not silently select another Broker. If the selected identity disappears or is replaced at the same address, select a current Broker explicitly. Runtime health and rates remain unknown when observations are missing; refresh timestamps describe dashboard reads rather than Broker last-seen events. A failed catalog or detail refresh retains prior data and does not advance the last successful page refresh time.

The configuration inspector supports key/value search, the existing Broker/Runtime/Storage/Messaging/Security categories, and copying values. The editor loads current string-valued properties and offers Fields and JSON views. Review computes a patch containing only changed keys. Empty keys, non-string JSON values, unsupported key removal, and property-line injection are rejected. Confirmation shows the Broker identity and every submitted key/value change.

The authenticated command `update_cluster_broker_config` holds the current connection revision lease and verifies cluster name, Broker name, Broker ID, and address against current discovery before writing through `DashboardAdmin`. It submits the patch once, then reads configuration once. The result separates an acknowledged write from read-back states `confirmed`, `different`, and `unavailable`. A read-back failure never turns the acknowledged write into a failed write or triggers a retry. Audit records the write outcome and Broker address without configuration values.

The editor owns its pending write outside the route's connection-revision key, so route remounts cannot discard its result. Connection changes freeze further reads and edits for that captured target, while an acknowledgement already in flight remains visible with its original Broker and environment. Changing the authenticated session disposes the old editor and prevents a late result from appearing for another user. Reads from an obsolete target are ignored.

Pending reads and writes prevent duplicate submissions and dialog dismissal. Closing an idle editor restores focus to its opener, or to the main content when the opener has been unmounted. An unconfirmed write or unavailable read-back requires a fresh read before another edit. A successful read-back replaces the draft with the values actually returned; a different read-back is reported without reapplying the patch. A later read retains the original operation receipt, and another change always requires fresh confirmation.

Validation covers identity mismatch and invalid input without writes, changed-key projection, successful writes with failed read-back, and audit classification. Configuration is not a compare-and-swap API: another administrator may change the same key concurrently, and the editor reports differing read-back values when observed.
